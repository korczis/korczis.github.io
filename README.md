# korczis.github.io

The personal hub of Tomas Korcak (korczis): <https://korczis.github.io/>. It covers who I am,
the projects I build with their live sites, the stack behind them, and
[Majordomus](https://majordomus.dev), which supervises the work.

The site uses Zola (Tera 2) with Flowbite Pro on Tailwind 4 and Alpine.js; its visuals go through
one component layer (`static/js/site.js`) over the libraries pinned in `package.json` and
self-hosted by `scripts/vendor.mjs`. It is supervised by Majordomus and deployed to GitHub Pages from
`master`. The decision is recorded in
[ADR 0001](.ai/repo/adrs/0001-personal-hub-on-zola-with-flowbite-pro-deployed-to-github-pa.md).

## Quick start

```sh
npm ci               # the locked tools; also points git at .githooks (doctor on commit, finish --check on push)
npm run dev          # vendor bundles + CSS once, then tailwind --watch next to zola serve on http://127.0.0.1:1111
npm run derive       # after editing data/, i18n/ or a generator: regenerate every derived page and file
npm run check        # every gate CI runs, without the browser (node scripts/gates.mjs run --ci)
npm run verify       # every gate, then the browser audit (-- --fast skips it, -- --from <id> resumes)
```

`npm run dev -- --port <n>` serves elsewhere; Ctrl-C stops both watchers. Every script answers
`--help` with its own header and refuses an unknown flag (exit 2); a stale derived file is always
fixed by `npm run derive`. The browser audit needs the Chromium headless shell once:
`npx playwright-core install chromium-headless-shell`.

## Languages

The site exists in English and Czech (`/cs/`) through Zola's multilingual features:
- **Interface texts:** `i18n/strings.toml` holds every text, with an `en` and a `cs` value per
  key. `npm run i18n` writes it into `zola.toml` and templates call `trans()`.
- **Data:** every text field has a `_cs` twin, read generically as `c["name" ~ sfx]`.
- **Pages:** every page is `x.md` plus `x.cs.md`. The generators write both versions of the
  category and work pages.
- **Tags:** tags are a Zola taxonomy, derived from categories and languages.
- **The gate:** `scripts/check-i18n.mjs` fails on any untranslated text (rule
  `project.i18n-everywhere`).

## Every page is an article

Each page also teaches: it carries an article (its Markdown body) that explains what it shows and
how to read it, and ends with **Concepts on this page**, the glossary terms it builds on.
- **Glossary:** `data/glossary.toml` defines each term (language, technology, concept) in English
  and Czech, with a source to read further. `npm run glossary` writes `content/glossary/`: one
  page per term and language, listing every page that uses it and the related terms. Both lists
  are derived from front matter.
- **Front matter:** `extra.terms` names a page's terms, and `extra.article_title` names its
  article. Generated pages get both from their generator (`scripts/lib/terms.mjs` resolves
  languages, stack and categories to terms by convention). Hand pages write them in `content/`.
- **Links:** articles link to terms with `@/glossary/<id>.md`, so Zola checks every link.
- **Machines:** JSON-LD `about` lists a page's terms as `DefinedTerm`, and term pages belong to
  the glossary's `DefinedTermSet`.
- **The gate:** `scripts/check-glossary.mjs` fails on a page without an article or terms, on an
  unknown or unused term, and on a term without a source (rule `project.pages-are-articles`).

## How the site stays current

Pages are front matter over data. Nothing on them is typed, so nothing needs updating by hand:
- **Front matter:** `content/*.md` carries it, checked against
  [`static/schemas/front-matter.schema.json`](static/schemas/front-matter.schema.json).
- **Data:** `data/projects.toml` holds the words. `data/github.json` and `data/index.json` hold
  the measurements.
- **Derived:** category pages, `llms.txt`, `llms-full.txt`, OG images and `site.json` (the whole
  site as data).
- **Refresh every six hours:** `.github/workflows/refresh.yml` is scheduled at 23 minutes past
  every hour (UTC), because GitHub drops scheduled runs under load. A scheduled run measures only
  when the data on master is older than `REFRESH_HOURS` (6) minus one hour and stops after the
  checkout otherwise; a dropped run then costs an hour, not six. A run checks out the tip of
  master, so one that waited behind another judges that run's data. After a failed scheduled run
  the next attempt waits the same 5 hours, so a red gate fails four times a day, not 24. By hand, `gh workflow run refresh.yml`
  always measures. It runs `npm run refresh`, then `npm run check`. Only when every
  gate passes does it commit to master and start the deploy.
  GitLab is read through one client (`scripts/lib/gitlab.mjs`): `glab` locally, REST in CI
  (`GITLAB_TOKEN` raises the limits, anonymous works). Every rate-limit wait is logged. Each
  fetcher has a 15-minute GitLab budget (`GITLAB_BUDGET_MS`), counted from its first GitLab call.
  Once it is spent, each project it no longer reaches keeps its last measurement (the listing is
  already read, so the GitLab, fork and mirror counts stay whole) and the run says how many; a
  refresh degrades, never hangs. An ownership
  share is measured again only for projects with new activity. The daily Monitor runs
  `scripts/check-fresh.mjs`, which fails when the data on master is older than 24 hours.

## Common tasks

- **Fill the CV.** Write roles, education and languages into `data/cv.toml` (its header shows the shape), then `npm run verify`; /about/ and the JSON-LD Person render them. The contact email is the GitHub profile's public email, measured by `npm run data`.
- **Add a project.** Add an entry to `data/projects.toml`, then run `npm run data` and `npm run derive`.
  `check-data.mjs` refuses forks, private repositories, dead live URLs and a hand-typed
  "Majordomus" in `stack`.
- **Refresh the numbers.** Run `npm run data` and `npm run index` (they need authenticated `gh` and
  `glab`), then `npm run derive`. Commit the results. Every page shows the date of its snapshot.
- **Change a category rule or the mirrors/hidden lists.** Edit `data/projects.toml` and run
  `npm run index -- --derive`. No network is needed.
- **Add a visual.** Create `static/js/viz/<name>.js` registering `KorczisHub.viz('<name>', …)`
  whose handle returns `items()` and `controls()`, declare it in front matter (`[[extra.viz]]`),
  then `node scripts/check-viz-layer.mjs --fix` adds it to the schema's enum. The same script
  enforces the layer.
- **Add a page.** Add the template and a `content/` entry with `title`, `description` and
  `[extra] og_title`, `og_image`, `schema` and `keywords`. Run `npm run og`; the browser audit
  picks one page per template and language from the sitemap by itself. Titles, Open Graph and Twitter tags and JSON-LD are derived
  from that front matter.

- **Change anything under `.ai/`.** Run `npm run interfaces -- --measure` (it needs `majordomus`), then
  `npm run derive`: `static/ai.json` is stamped with the tracked `.ai/` tree, and the `interfaces` gate
  refuses a change to `.ai/` that was not indexed again. /interfaces/ and the topbar's interfaces menu
  (tiles from `data/nav.toml [[interfaces]]`) read it, with `static/openapi.json`.

- **Add a gate.** Add one entry to `GATES` in `scripts/gates.mjs` and run
  `node scripts/gates.mjs readme`; check, verify, CI and the refresh run it from there.

## Deploy

A push to `master` runs `.github/workflows/pages.yml` in three stages:

1. `ci`: the same workflow pull requests run.
2. `deploy`: reads the validated artefact once more for denylisted names, then deploys it to
   Pages (once more with a fresh upload when the Pages API has not yet seen the artefact).
3. `verify`: checks that production serves `revision.txt` equal to the commit and that every
   section page, script, stylesheet and machine-readable file it serves is byte-identical to the
   artefact (the list is read from the artefact). It then runs the same browser audit against the
   public site and asks every linked live project whether it answers.

`.github/workflows/ci.yml` runs once per pull request into `master` and as this first stage; a
branch push does not run it a second time. A branch without a pull request is checked by its
pre-push hook, or on demand with `gh workflow run ci.yml --ref <branch>`.

`.github/workflows/monitor.yml` repeats that production check every day, and you can also start
it by hand from the Actions tab.

The repository is public and declares `ui.kit: flowbite-pro`. Because of that, CI's
`majordomus doctor` fails closed until the owner stores the licence evidence. Do it once:

```sh
~/.claude/skills/flowbite-pro/evidence.sh secret | \
  gh secret set MAJORDOMUS_KIT_EVIDENCE_FLOWBITE_PRO -R korczis/korczis.github.io
```

## Repository settings

These are set through the GitHub API (`gh api`), not in files:
- description, homepage and topics;
- wiki, projects and discussions are off; branches are deleted on merge; auto-merge is allowed;
- Pages: `build_type: workflow`, HTTPS enforced;
- secret scanning with push protection, Dependabot alerts and security fixes (and
  `.github/dependabot.yml` for weekly grouped updates);
- ruleset "master: history is append-only", which blocks deleting `master` and force-pushing to it;
- secrets `MAJORDOMUS_KIT_EVIDENCE_FLOWBITE_PRO` and `NDA_DENYLIST` (for Actions, and for
  Dependabot so its pull requests pass the same gates); optional variable `PAGES_RUNNER` (ADR 0002).

## Working on this repository

The repository is supervised by Majordomus. AI workers start from [`AGENTS.md`](AGENTS.md)
(Claude Code: `CLAUDE.md`, Gemini: `GEMINI.md`, all generated from `.ai/repo/policy.yaml`). They
run `majordomus context` and work in a branch under `korczis.github.io-wt/<branch>`
(`majordomus worktree create <branch>`). A task closes with `majordomus finish` once
`npm run verify` has passed.
